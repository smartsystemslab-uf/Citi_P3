# Citi Bank P3 — Banking Backend and ADK Integration

This project contains a runnable banking demo system for the Citi P3 multi-agent workflow.

The system has two main parts:

1. **Banking Backend**: a FastAPI service with SQLite databases for customers, accounts, transactions, policies, and risk rules.
2. **Google ADK Agent System**: the original multi-agent workflow that calls the backend through HTTP tools.

The tested local workflow is:

```text
Google ADK Agents
        |
        | HTTP tool calls
        v
FastAPI Banking Backend
        |
        v
SQLite Database
```

The backend provides the database-backed API layer used by the agents. The agents no longer rely only on hard-coded mock data. They can retrieve customer context, search policies, evaluate transaction risk, and execute banking actions through controlled APIs.

## 4. Backend API Overview

Important endpoints:

```text
GET  /health
POST /customers
GET  /customers/{customer_id}
GET  /customers/{customer_id}/accounts
GET  /customers/{customer_id}/context
GET  /customers/{customer_id}/transactions

POST /accounts
GET  /accounts/{account_id}

GET  /transactions
GET  /transactions/{transaction_id}

POST /monitoring/evaluate_transaction
POST /banking-api/transfer

POST /policies
GET  /policies
GET  /policies/search

POST /rules
GET  /rules
```

Main API roles:

| API | Purpose |
|---|---|
| `/customers/{customer_id}/context` | Returns customer profile, accounts, and recent transactions |
| `/policies/search` | Searches policy database for compliance/RAG agents |
| `/rules` | Lists active risk rules |
| `/monitoring/evaluate_transaction` | Evaluates transaction risk without executing transfer |
| `/banking-api/transfer` | Executes a transfer and writes a transaction record |

## 9. Configure ADK to Use the Backend

Create or edit this file:

```text
citi_banking_adk\.env
```

Add:

```env
BANKING_BACKEND_BASE_URL=http://127.0.0.1:8000
BANKING_USE_EXTERNAL_API=true
```

This tells the ADK tools to call the FastAPI backend instead of only using local mock data.

To temporarily disable the external backend, set:

```env
BANKING_USE_EXTERNAL_API=false
```

## 11. Run ADK Scenarios

Keep the backend server running.

From the ADK folder:

```powershell
python run_scenarios.py --scenario front_office_transaction_execution
```

Expected behavior:

1. `user_proxy_agent` routes the request.
2. `front_office_router` sends it to the customer service workflow.
3. `transaction_processing_agent` calls the tool `execute_transfer`.
4. The tool calls the backend endpoint `/banking-api/transfer`.
5. The backend returns a completed transaction.

A successful result should include:

```text
event: tool_call
tool: execute_transfer

event: tool_result
status: completed
risk_score: 0

raw_backend_result
```

The `raw_backend_result` field confirms that the ADK workflow called the backend API.

Run the monitoring scenario:

```powershell
python run_scenarios.py --scenario front_office_monitoring
```

Run all scenarios:

```powershell
python run_scenarios.py --scenario all
```

## 12. How to Understand the System

### Swagger UI

The page at:

```text
http://127.0.0.1:8000/docs
```

is a developer API console.

It allows manual testing of the same APIs that the ADK agents call automatically.

```text
Manual test in Swagger UI
        =
Agent tool call from ADK
```

For example:

```text
POST /banking-api/transfer
```

is manually tested in Swagger, but in the ADK workflow it is called by:

```text
transaction_processing_agent -> execute_transfer()
```

### Backend

The backend is the source of truth for:

```text
customer profile
account records
transaction records
policy records
risk rules
risk evaluation
transfer execution
```

### ADK

The ADK system is the orchestration layer. It decides which agent should act and which tool/API should be called.

## 14. Common Issues

### `ModuleNotFoundError: No module named 'app'`

Run from the backend root folder:

```powershell
cd D:\Lab\Citi-Bank-P3\citi_banking_backend
$env:PYTHONPATH = (Get-Location).Path
python scripts\init_db.py
```

Or update `scripts/init_db.py` to insert the project root into `sys.path`.

### `Activate.ps1 is not recognized`

This means `.venv` does not exist in the current folder.

Create it:

```powershell
py -3.11 -m venv .venv
```

Then activate:

```powershell
.\.venv\Scripts\Activate.ps1
```

### PowerShell blocks activation

Run:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
```

### ADK cannot reach backend

Make sure the backend server is running:

```powershell
cd D:\Lab\Citi-Bank-P3\citi_banking_backend
.\.venv\Scripts\Activate.ps1
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Then check:

```text
http://127.0.0.1:8000/docs
```

Also confirm `citi_banking_adk\.env` contains:

```env
BANKING_BACKEND_BASE_URL=http://127.0.0.1:8000
BANKING_USE_EXTERNAL_API=true
```

### Policy search returns empty

Try searching simple keywords:

```text
AML
KYC
fraud
large transfer
```

If searching a multi-word query, the backend should tokenize the search query and match policies by keyword.

## 15. Demo Explanation

A concise explanation for reports or presentations:

> We implemented a FastAPI-based banking backend with SQLite demo databases for customer profiles, accounts, transactions, policies, and risk rules. The original Google ADK multi-agent workflow is integrated with this backend through HTTP tool calls. This allows the agents to retrieve real structured context, search compliance policies, evaluate transaction risk, and execute banking actions through controlled APIs instead of relying only on hard-coded mock data.

More detailed explanation:

> The Swagger UI provides a developer-facing test console for the banking backend. Through this interface, we can manually validate customer context retrieval, account lookup, transaction history, policy search, rule-based risk evaluation, and transfer execution. In the actual multi-agent workflow, the Google ADK agents call the same APIs automatically through their tool functions. This gives the system a clear separation between agent orchestration, backend business logic, and persistent data storage.
